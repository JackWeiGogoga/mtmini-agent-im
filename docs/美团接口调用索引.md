# 美团接口调用索引

## 范围与成本约束

- `backend/` 是唯一真实调用美团开放平台的模块；`frontend/` 与 `h5/` 只调用本系统接口。
- 授权后的 IM 初始化只调用两个固定写接口，不调用“查询门店 IM 状态”或“查询智能回复机器人开关状态”做前置判断、写后确认或重试确认。
- 机器人开关查询接口是付费接口，项目代码、测试和运维流程均禁止调用。固定写操作由数据库异步任务按既定参数重试。
- `/imMsg` 同步范围包含验签、解析、解密、统一时间线入库，并在同一数据库事务内创建自动回复占位与异步任务；回调线程不调用 Embedding、Chat、算力或美团发送接口。
- 独立异步任务通过 `biz_type=1` 两方会话发送客户端发送回复；客户端不调用状态查询接口，也不在内部重试，任务层使用持久化的稳定 `msg_id` 重试。
- 所有美团 SDK 出站方法统一经过 `MtDryRunMeituanClient`。`mt.api.dry-run` 默认 `true`，覆盖 OAuth、Token 刷新、所有 typed/common 查询和写接口；只有显式设置 `MT_API_DRY_RUN=false` 才会真实委托 SDK。

## 全局 Dry Run

- 配置：`mt.api.dry-run=${MT_API_DRY_RUN:true}`，无损重排间隔为 `mt.api.dry-run-reschedule-seconds=${MT_API_DRY_RUN_RESCHEDULE_SECONDS:3600}`。
- 边界：Spring 中唯一的 `MeituanClient` Bean 由 dry-run 代理包装，覆盖四种 `invokeApi` 重载、`commonInvokeApi`、`getOAuthToken` 和 `refreshToken`，因此下表全部 SDK 调用都受同一个开关控制。
- 命中行为：不调用真实 SDK、不构造虚假成功响应；数据库异步任务抛出统一 dry-run 信号并无损重排，不增加重试次数，同步调用快速失败。
- 日志：只记录 SDK 方法和 Request 类型，不记录 access/refresh token、OAuth code、请求正文、消息正文、密文或完整响应。
- 本地联调：执行 `deploy-local/本地测试数据.sql` 后，可使用 `http://localhost:5173/?wmPoiId=TEST_EPOI_REPLY_001&platform=local-test` 直登，不依赖真实美团 OAuth，也不需要关闭 dry-run。
- 真实联调：仅在确认目标环境、开发者账号和门店后临时设置 `MT_API_DRY_RUN=false` 并重启后端；关闭前必须检查 `mt_async_task` 待执行积压，避免 dry-run 期间保留的任务被集中真实执行，联调结束后恢复为 `true`。

## IM 发送 Dry Run

- 配置：`mt.api.im-send-dry-run=${MT_API_IM_SEND_DRY_RUN:false}`，只作用于 `SendImMsgWmoperRequest`（`biz_type=1` 两方会话消息发送）。
- 语义：在总开关之上额外收紧，不能放宽。总开关为 `true` 时 IM 发送必然被阻断；只有总开关为 `false` 时该开关才生效，设为 `true` 可在其它美团接口真实调用的前提下单独阻断 IM 消息外发。
- 命中行为与总开关一致：抛出同一 dry-run 信号，异步任务无损重排，不增加重试次数；日志 `reason` 字段区分 `GLOBAL_DRY_RUN` 与 `IM_SEND_DRY_RUN`。

## 授权后的 IM 初始化

授权核心数据提交后，`MtAuthAsyncTaskService` 以门店和授权事件生成幂等键，入队 `AUTH_CONFIGURE_IM`。worker 每次执行都会重新读取当前门店 token，并严格按以下顺序处理：

1. 开启门店 IM；
2. 关闭美团全部智能回复机器人开关；
3. 将本地 `mt_im_auto_reply_setting.auto_reply_enabled` 开启，并记录 `AUTH` 来源历史。

任一远端写操作失败时，本地开关保持关闭，任务按数据库策略重试；重试只重复固定写操作，不增加查询调用。

### 设置门店 IM 状态

- 文档：<https://developer.meituan.com/docs/api/wmoper-ng-im-setPoiIMStatus>
- SDK request：`SetPoiImStatusRequest`
- 固定参数：`imStatus=1`
- 实现：`backend/src/main/java/com/gogoga/backend/client/MtImConfigurationClient.java`

### 设置门店智能回复机器人开关状态

- 文档：<https://developer.meituan.com/docs/api/wmoper-ng-im-autosend-setAutoSendConfigInfo>
- SDK request：`SetAutoSendConfigInfoRequest`
- 固定参数：`allStatus=[{"type":0,"switchStatus":0}]`
- 语义：`type=0` 操作全部开关，`switchStatus=0` 关闭。

响应日志只保留阶段、返回码、traceId 和是否存在数据，不输出 token、请求秘密或完整上游正文。

## 接收 IM 两方会话消息

- 文档：<https://developer.meituan.com/docs/msg/msg_waimaing_0667a278-09c5-4d5d-98b3-6a92b5d3cfd8>
- 本地入口：`POST /api/callbacks/meituan/imMsg`
- 格式：`application/x-www-form-urlencoded`
- 验证：使用配置的 `mt.sign-key` 对外层全部非空参数验签，并校验 `developerId`、`businessId`；内层 `sig` 只留存，不替代外层验签。
- 解析：兼容 `message.push_content` 为 JSON 对象或转义字符串，原始 JSON 保留未知扩展字段。
- 门店关联：优先使用内层 `app_poi_code` 匹配 `mt_shop.epoi_id`，再回退外层 `ePoiId`。
- 解密：使用 `mt.im.secret`；成功保存密文、明文与 SHA-256，失败保存安全状态和摘要。
- 消息类型：接收协议声明 `msg_type=1` 文本、`2` 图片、`3` 其他、`17` 卡片；当前均可透明入库，未知类型也不在接收侧丢弃。
- 图片/媒体边界：图片内容按协议密文解密后原样保存，当前不做下载、结构化解析或展示处理；官方没有独立的视频类型，若上游把视频类扩展作为 `msg_type=3` 推送，只按“其他”消息透明保存。
- 入库：不按 `msg_source`、`msg_type`、`has_reply` 或零值 `order_id` 过滤；门店未匹配、解析不完整或解密失败也要落库后返回成功。合法顾客文本会关联 Conversation/Session，并在同一事务创建自动回复记录和异步任务。
- 幂等：`callback_msg_id` 唯一，且 `(app_id, platform_msg_id)` 唯一。
- 响应：确认落库或确认重复后返回 `{"code":0,"message":"success"}`；验签/协议失败或数据库结果未知时返回非 0。

普通日志不得输出消息正文、完整 payload、完整密文、token 或 `mt.im.secret`。

## 发送 IM 两方会话消息

- 文档：<https://developer.meituan.com/docs/api/wmoper-ng-im-msg-send>
- SDK request：`SendImMsgWmoperRequest`
- 本地实现：`backend/src/main/java/com/gogoga/backend/client/MtImMessageClient.java`
- 固定上下文：`biz_type=1`、`msg_source=1`（商家）、`has_reply=2`；不再使用评价匿名群聊的 `biz_type=4`、`comment_id`、`group_id`。
- 发送类型：只放行两方会话接口声明的 `msg_type=1` 文本、`2` 图片、`3` 其他；`17` 卡片只在接收协议中声明，发送客户端会拒绝；不存在独立的视频发送类型。
- 敏感词：`msg_type=1` 文本在加密前复用通用 `SensitiveWordService`；命中时返回 `SENSITIVE_WORD_HIT`，安全摘要只包含类别、命中数和最高严重级别，不加密正文且不调用美团。图片和“其他”类型正文按 URL、JSON 或 Base64 等不透明协议载荷处理。
- 加密：调用方传入明文内容，客户端复用 `mt.im.secret` 按 AES/CBC/PKCS5Padding 加密后设置 `msg_content`。
- 会话参数：调用方传入稳定且唯一的 `msg_id`、10 位秒级 `cts`、`order_id`、`open_user_id` 和场景字段；同一业务消息重试时必须复用 `msg_id`。
- 调用边界：客户端每次方法调用只请求一次美团发送接口，不生成消息 ID、不查询机器人或 IM 状态、不做内部重试、不生成回复、不扣算力。
- 自动回复任务在回调事务提交后独立执行；回调线程从不直接调用该客户端。任务发送前再次检查更新顾客消息和人工回复，重试始终复用已持久化的正文与 `msg_id`。
- Dry run：全局开关开启时，发送调用在 SDK delegate 前被阻断；任务保留已生成正文、算力记录和稳定 `msg_id` 后无损重排，不标记 `SENT`。

## 定时消息群发

- 复用同一个 `MtImMessageClient.sendTwoPartyMessage`，不新增任何美团接口；群发是该接口的第二个调用场景。
- 群发消息不依附订单：`order_id` 传 `0`，`scene_tag`/`scene_name`/`extended_field` 留空，客户端 `order_id >= 0` 的既有校验已放行。
- 任务分级：调度（每分钟建批次）→ `IM_BROADCAST_PLAN`（游标翻页物化明细并分片）→ `IM_BROADCAST_SEND`（分片实发）。调度本身不调用美团。
- 目标人群：`mt_im_conversation` 中 `last_user_message_at` 在近 `mt.im-broadcast.active-within-days` 天内的顾客，按 `(last_user_message_at, id) DESC` 游标扫描并按 `max-targets-per-batch` 截断。刻意不使用 `last_message_at`，否则群发自身会把顾客永久留在活跃窗口内。
- 限流：全局 Redis 令牌桶约束 `sendImMsgWmoper` 总 QPS（`mt.im-broadcast.global-qps`，频控未知时保守取 20），单门店信号量约束并发分片数，触发点按 `shopId` 哈希抖动削峰。
- 幂等：`outbound_message_id` 在编排阶段固化并持久化，分片重试复用同一 ID；已 `SENT` 的明细不再重发。
- 敏感词：文案在保存时与批次编排时各检测一次，命中即整批 `SKIPPED`，不进入逐条发送。
- 触发水位：保存配置时若当天的时间点已过，`last_trigger_date` 直接落在今天，避免下一轮扫描判定「已到点」立刻补发一批；时间点未到则清空水位，当天照常触发。
- 变更审计：保存与删除各写一条 `mt_im_broadcast_setting_history`，记 `change_type`（SAVE/DELETE）、`change_source`（H5/ADMIN）、操作人、星期/频率/时间/文案全文与前后快照 JSON。删除记录里存的是被删掉那一版的配置，否则记录无信息量。总控台「群发配置 → 变更历史」页签查看。文案全文只入业务表，普通日志仍不输出正文。
- 失效回显：「一次」触发后只置 `enabled=0`，星期/频率/时间/文案原样保留供回显；只有商家显式删除才 `clearSchedule` 清空字段。`configured` 仅由 `enabled` 决定。
- 状态口径：`configured` 只回答「当前有没有在跑的定时任务」，供 H5 决定按钮形态；运营侧用 `status`（`NONE`/`ACTIVE`/`ONCE_COMPLETED`）区分「从没配过或已删除」与「一次性已执行完成」。状态由后端依据 `enabled + repeat_mode + week_days 是否被清空 + last_trigger_date` 统一判定，前端不得自行组合推断。
- 配置入口：H5 首页与后台总控台共用 `MtImBroadcastSettingService`，校验（星期、频率、字数、敏感词）和「一次触发后失效」语义完全一致。总控台按 `requireCurrentUserVisibleShop` 做门店可见性校验，越权门店不可读写。
- 算力：群发不走大模型，不做算力记账。
- 与「一键开启 AI 回复」总开关相互独立，只受群发总开关、门店权益与授权态约束。
- Dry run：同样经过 `MtDryRunMeituanClient`，全局开关开启时分片任务无损重排，明细保持 `PENDING`。

## 自动回复异步编排

- 触发条件：只处理已匹配门店、成功解密、`biz_type=1`、`msg_source=2`、`msg_type=1` 且正文非空的顾客消息；仍受门店授权、权益、算力、本地开关和全局灰度开关约束。
- 会话边界：`(shop_id, open_user_id)` 是长期 Conversation；默认空闲 30 分钟新建子 Session，`order_id` 变化不会切分。模型只读取当前 Session 最近 100 轮，管理查询可跨全部历史 Session。
- 连续消息：任务默认延迟 2 秒；同 Conversation 的新顾客消息会淘汰旧任务，触发消息后存在人工回复则跳过，生成后发送前再次复核。
- RAG：门店存在可用知识时，对当前问题和最近三次顾客提问生成 Embedding，并执行门店隔离的 topK/阈值召回；知识异常触发任务重试，不跨店召回。
- 状态与计费：`PENDING → GENERATING → GENERATED → BILLED → SENDING → SENT`，另有 `SUPERSEDED/SKIPPED/DEAD`；按模型实际 usage 生成稳定算力请求号幂等记账。
- 回推合并：内部 AI 消息先进入统一时间线；美团回推相同 `(app_id, platform_msg_id)` 时补全原记录，不重复创建消息。
- 安全日志：任务、模型、发送和查询服务只记录安全 ID、状态与错误码，不输出正文、完整 prompt、知识片段、密文、token 或上游完整响应。

上游响应摘要只保留返回码、traceId 和是否存在数据；本地敏感词失败只保留类别、命中数和最高严重级别。两者均不输出 access token、消息明文、具体命中词、密文或上游完整错误正文。

## 其他保留链路

- 授权后仍通过 `AUTH_BLOCK_ORDER_PUSH` 关闭订单类消息推送；项目不接收或保存外卖订单推送数据。
- `AUTH_BACKFILL_POI_ID` 只读取订单 ID 和详情中的 `poiId`，不保存订单明细。
- 权益同步、订阅订单拉取、token 刷新、H5 直登和美团活动页跳转继续沿用原有门店隔离与幂等约束。
