# 推广数据库异步任务运维手册

## 适用范围

本手册覆盖以下数据库异步任务：

- `PROMOTION_AUTO_BID`
- `PROMOTION_LOG_MARKDOWN`

任务持久化表为 `mt_async_task`，商家侧执行结果仍以 `mt_promotion_bid_record` 为准。

## 关键开关

- `mt.promotion.async-task.enabled`
  说明：是否启用数据库异步任务模式。关闭后自动调价回退为旧的同步执行链路。
- `mt.promotion.async-task.worker-enabled`
  说明：是否启用数据库异步 worker。仅在 `enabled=true` 时生效。
- `mt.promotion.async-task.dispatch-page-size`
  说明：自动调价候选门店游标分页大小。
- `mt.promotion.async-task.poll-size`
  说明：单次轮询最多领取的任务数。
- `mt.promotion.async-task.poll-delay-ms`
  说明：worker 轮询间隔。
- `mt.promotion.async-task.recovery-delay-ms`
  说明：超时回收扫描间隔。
- `mt.promotion.async-task.cleanup.enabled`
  说明：是否启用历史终态任务清理。
- `mt.promotion.async-task.cleanup.delay-ms`
  说明：历史终态任务清理扫描间隔。
- `mt.promotion.async-task.cleanup.batch-size`
  说明：单次每种终态最多清理条数。
- `mt.promotion.async-task.cleanup.success-retention-days`
  说明：`SUCCESS` 任务保留天数。
- `mt.promotion.async-task.cleanup.dead-retention-days`
  说明：`DEAD` 任务保留天数。
- `mt.promotion.async-task.auto-bid-shop-lock-seconds`
  说明：单店自动调价互斥锁时长。
- `mt.promotion.async-task.auto-bid-busy-backoff-seconds`
  说明：同店锁冲突时的无损重排退避时长。

## 状态说明

`mt_async_task.status`：

- `PENDING`：待执行，`available_at` 到时后可被领取
- `PROCESSING`：已被某个 worker 领取
- `SUCCESS`：执行成功
- `DEAD`：超过重试预算后的终态失败

历史清理规则：

- 系统只清理终态任务：`SUCCESS`、`DEAD`
- `PENDING`、`PROCESSING` 永不参与自动清理
- 清理按状态分批执行，避免一次性大事务

`mt_promotion_bid_record`：

- 只保留商家可见的终态业务结果，例如 `SUCCESS / SKIPPED / FAILED`
- 不承载 dispatch、claim、retry 这类技术态
- `log_markdown_status` 用于表示日志 Markdown 的可见状态：`PENDING / READY / FALLBACK`
- `log_task_id` 用于关联对应的 `PROMOTION_LOG_MARKDOWN` 任务，便于按记录反查异步任务

`MtH5PromotionLogVO.markdownStatus`：

- `READY`：Markdown 已由异步任务生成
- `FALLBACK`：异步任务已落回退文案

用户侧日志列表行为：

- `log_markdown_status = PENDING` 的执行记录不会出现在用户日志列表中
- 只有 Markdown 生成成功并标记为 `READY`，或生成失败后落兜底并标记为 `FALLBACK`，该记录才会对用户可见
- 因此，`PENDING` 只是一种后台排障态，不是用户可见态

## 常用排查 SQL

查询任务积压：

```sql
SELECT task_type, status, COUNT(*) AS cnt
FROM mt_async_task
GROUP BY task_type, status
ORDER BY task_type, status;
```

查询即将执行或已积压的任务：

```sql
SELECT id, task_type, biz_key, scope_key, status, retry_count, available_at, claimed_at, worker_id, last_error
FROM mt_async_task
WHERE status = 'PENDING'
ORDER BY available_at ASC, id ASC
LIMIT 100;
```

查询超时未完成任务：

```sql
SELECT id, task_type, biz_key, scope_key, retry_count, claimed_at, worker_id, last_error
FROM mt_async_task
WHERE status = 'PROCESSING'
ORDER BY claimed_at ASC
LIMIT 100;
```

查询死信任务：

```sql
SELECT id, task_type, biz_key, scope_key, retry_count, last_error, finished_at
FROM mt_async_task
WHERE status = 'DEAD'
ORDER BY finished_at DESC, id DESC
LIMIT 100;
```

查询可被历史清理命中的任务：

```sql
SELECT id, task_type, status, finished_at, biz_key, scope_key
FROM mt_async_task
WHERE status IN ('SUCCESS', 'DEAD')
  AND finished_at IS NOT NULL
ORDER BY finished_at ASC, id ASC
LIMIT 100;
```

按门店查看自动调价任务与业务记录：

```sql
SELECT id, task_type, biz_key, status, retry_count, available_at, claimed_at, last_error
FROM mt_async_task
WHERE scope_key = '门店ID'
ORDER BY id DESC
LIMIT 50;

SELECT id, shop_id, slot_time, execute_status, decision_reason, markdown_message
FROM mt_promotion_bid_record
WHERE shop_id = 门店ID
ORDER BY slot_time DESC, id DESC
LIMIT 50;
```

按执行记录反查 Markdown 任务状态：

```sql
SELECT r.id,
       r.shop_id,
       r.slot_time,
       r.execute_status,
       r.log_markdown_status,
       r.log_task_id,
       t.status AS task_status,
       t.retry_count,
       t.available_at,
       t.claimed_at,
       t.last_error
FROM mt_promotion_bid_record r
LEFT JOIN mt_async_task t ON t.id = r.log_task_id
WHERE r.shop_id = 门店ID
ORDER BY r.slot_time DESC, r.id DESC
LIMIT 50;
```

## 手工恢复策略

### 1. `PENDING` 长期积压

优先检查：

- `mt.promotion.async-task.worker-enabled` 是否已打开
- 应用日志中是否存在 claim / success / retry 日志
- 数据库是否出现大量同店锁冲突 `SHOP_EXECUTION_BUSY`

如果只是 worker 暂停，恢复 worker 后任务会继续消费，一般不需要改表。

### 2. `PROCESSING` 长期不结束

系统会按任务类型超时策略自动回收。若确认实例已经异常退出但回收尚未发生，可等待下一次 recovery 扫描；不建议直接手改为 `SUCCESS`。

### 3. `DEAD` 死信任务

先看 `last_error`：

- 如果是上游接口短暂异常，可人工回补为 `PENDING`
- 如果是配置错误、授权失效、门店状态异常，先修业务数据再重试

推荐手工恢复方式：

```sql
UPDATE mt_async_task
SET status = 'PENDING',
    retry_count = 0,
    available_at = NOW(),
    claimed_at = NULL,
    finished_at = NULL,
    worker_id = NULL,
    update_time = NOW()
WHERE id = 任务ID
  AND status = 'DEAD';
```

### 4. 单门店频繁失败

优先看：

- `last_error`
- 是否持续出现 `SHOP_EXECUTION_BUSY`
- `mt_promotion_bid_record.decision_reason` 与 `error_msg`
- `mt_promotion_bid_record.log_markdown_status` 是否长期停留在 `PENDING`

该场景下系统已做同店互斥和失败退避，不建议为了追赶任务直接提高全局 worker 并发，应优先修复该门店异常原因。

### 5. 用户反馈“某条执行日志没显示”

优先检查：

- `mt_promotion_bid_record` 是否已经写入该次执行记录
- `log_markdown_status` 是否仍为 `PENDING`
- `log_task_id` 对应的 `PROMOTION_LOG_MARKDOWN` 任务是否仍在 `PENDING / PROCESSING / DEAD`

说明：

- 这是当前设计的预期行为
- 只要日志 Markdown 还没生成成功或失败落兜底，该执行记录就不会出现在用户日志列表
- 如果需要人工恢复，应优先恢复对应的 `PROMOTION_LOG_MARKDOWN` 任务，而不是直接修改业务执行记录为可见

### 6. `mt_async_task` 表持续增长

优先检查：

- `mt.promotion.async-task.cleanup.enabled` 是否已开启
- `cleanup.delay-ms`、`batch-size` 是否过小，导致清理追不上新增速度
- 是否存在大量历史 `DEAD` 任务长期无人处理

说明：

- 系统会自动分批清理超过保留期的 `SUCCESS` / `DEAD` 任务
- 如果历史积压已经很大，建议先在低峰期多次手动执行分批删除，不要一次性全表大删

推荐手工分批清理方式：

```sql
DELETE FROM mt_async_task
WHERE status = 'SUCCESS'
  AND finished_at < NOW() - INTERVAL 7 DAY
ORDER BY finished_at ASC, id ASC
LIMIT 1000;

DELETE FROM mt_async_task
WHERE status = 'DEAD'
  AND finished_at < NOW() - INTERVAL 30 DAY
ORDER BY finished_at ASC, id ASC
LIMIT 1000;
```

## 灰度建议

1. 先在测试或预发环境开启 `mt.promotion.async-task.enabled=true`，`worker-enabled=false`，只验证 dispatch 是否正常入库。
2. 再开启 `worker-enabled=true`，观察 `mt_async_task` 是否按预期从 `PENDING -> PROCESSING -> SUCCESS/DEAD` 流转。
3. 小流量生产环境先打开数据库异步任务模式，关注：
   - `PENDING` 是否快速堆积
   - `DEAD` 是否持续增长
   - `PROMOTION_LOG_MARKDOWN` 是否明显滞后
   - `mt_promotion_bid_record.log_markdown_status = PENDING` 是否出现异常滞留，导致用户日志长期不可见
   - 历史 `SUCCESS` / `DEAD` 任务是否按保留期逐步被清理
4. 灰度稳定后再全量启用。

## 回滚说明

若需要回滚到旧同步模式：

1. 关闭 `mt.promotion.async-task.enabled`
2. 保持 `worker-enabled=false`
3. 已存在的 `mt_async_task` 数据可保留，不会破坏既有 `mt_promotion_bid_record`

注意：

- 回滚后新的自动调价不再依赖 `mt_async_task`
- 历史未消费的异步任务不会自动清空，后续若重新启用 worker 仍可能继续执行，因此回滚前要先确认是否需要保留这些待执行任务
