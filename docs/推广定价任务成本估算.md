# 推广定价任务成本估算

## 1. 目的

- 用于估算“每次推广定价任务”的外部成本。
- 本文重点只拆两类：
  - 大模型 token 成本
  - 美团接口成本
- 口径以当前仓库代码和 [美团接口调用索引](/Users/jackwei/data/outsourcing/takeout-master-ai/mtmini-agent/docs/美团接口调用索引.md) 为准。

## 2. 先说结论

- 不是每个美团接口都收费。是否收费、价格多少，必须以 [美团接口调用索引](/Users/jackwei/data/outsourcing/takeout-master-ai/mtmini-agent/docs/美团接口调用索引.md) 的“费用说明”为准。
- 当前自动调价主链路里，大部分美团接口都是免费接口；真正会落到人民币成本的，美团侧当前主要是“补齐门店营业时间时查询门店详情”这一类收费管理 API。
- 当前“定价决策”本身并没有真正调用 LLM。
  - `PromotionBidDecisionService` 当前固定走规则引擎。
  - `decisionMode` 虽然允许配置 `llm`，但现阶段没有落到实际的 LLM 定价调用。
- 当前已经接入 LLM 的，是“推广日志 Markdown 生成”，不是“定价决策”本身。
- 当前推广计划写接口仍默认 `dry run`：
  - 更新推广计划状态：免费，但默认不真实外呼
  - 更新推广计划出价：免费，但默认不真实外呼

所以按“当前线上代码口径”估算：

- 单次定价主任务的 LLM token 成本：通常为 `0`
- 单次定价主任务的美团付费接口成本：通常也为 `0`
- 真正容易持续产生的成本，当前更像是：
  - 少量收费管理 API 的偶发调用
  - 成功记录生成日志时的 LLM token 成本

## 3. 当前主链路拆分

### 3.1 定时触发频率

- 自动调价任务由 `MtPromotionAutoBidTask` 按 `10` 分钟执行一次。
- 每个候选门店在每个槽位，最多执行一次。

粗略上限：

- 单店每天最多 `144` 个槽位
- 月槽位上限约 `144 x 当月天数`

但真正有成本的，不是所有槽位，而是“执行到哪些分支”。

### 3.2 定价主链路里的大模型

当前代码事实：

- `PromotionBidDecisionService` 返回的 `decisionSource` 固定是 `rule`
- `PromotionDecisionResult.llmTotalTokens` 当前被置为 `null`
- 定价算力扣减当前也按规则模式 `RULE` 执行

因此：

- 当前“定价主链路”不应计入 LLM token 人民币成本
- 如果你在报表里看“每次推广定价任务成本”，建议把 LLM 成本拆成：
  - `定价决策 LLM 成本`：当前为 `0`
  - `日志生成 LLM 成本`：当前可能大于 `0`

### 3.3 定价主链路里的美团接口

下表只列“和定价任务直接相关”的接口，并区分“是否收费”。

| 接口 | 当前调用时机 | 单次任务常见调用次数 | 是否收费 | 当前价格口径 |
| --- | --- | ---: | --- | --- |
| `/wmoper/ng/poi/detail` | 候选门店 `shipping_time` 为空时，先补齐营业时间 | `0~1` | 是 | `0.3 元 / 百次` |
| `/wmoper/ng/waimaiad/plan/status/info` | 进入可执行窗口后，校验远端计划状态/预算 | `1` | 否 | 免费 |
| `/wmoper/ng/waimaiad/balance` | 进入指标采集阶段后，读取余额与累计消耗 | `1` | 否 | 免费 |
| `/wmoper/ng/waimaiad/common/decrypt` | 解密余额、预算已用、实时广告金额、附近商家均价等字段 | `多次` | 否 | 免费 |
| `/wmoper/ng/waimaiad/data/detail` | 采集当前槽位实时广告快照 | 常见 `1` | 否 | 免费 |
| `/wmoper/ng/waimaiad/peer/bidprice` | 窗口首次调价或低峰重算基准价时查询附近均价 | `0~1` | 否 | 免费 |
| `/wmoper/ng/waimaiad/plan/update/bid` | 生成下一时段出价后写回美团 | 代码路径会走到，但默认不真实外呼 | 否 | 免费 |

说明：

- 这里的收费判断，来自 [美团接口调用索引](/Users/jackwei/data/outsourcing/takeout-master-ai/mtmini-agent/docs/美团接口调用索引.md)。
- 对“每次任务人民币成本”来说，免费接口不计费，但仍建议统计调用次数，因为它们会影响：
  - QPS
  - 时延
  - 重试放大
  - 上游限流风险

## 4. 单次任务该怎么估算

## 4.1 当前上线口径

当前单次“定价主任务”可以先按下面估算：

```text
单次主任务成本
= 美团收费接口成本
+ 定价决策 LLM 成本
```

当前代码下又可以进一步简化为：

```text
单次主任务成本
= 0.003 x N_门店详情补齐调用次数
+ 0
```

其中：

- `0.003` 元 = `0.3 元 / 百次`
- `N_门店详情补齐调用次数` 取值通常是 `0` 或 `1`

所以当前主链路最常见的两种情况是：

1. 门店营业时间已齐全

```text
单次主任务成本 = 0 元
```

2. 门店营业时间缺失，触发一次 `/wmoper/ng/poi/detail`

```text
单次主任务成本 = 0.003 元
```

## 4.2 把日志 LLM 也算进去

如果你的“每次推广定价任务成本”想按业务视角把日志也算进去，建议拆成：

```text
单次任务总成本
= 单次主任务成本
+ 单次日志 LLM 成本
+ 日志前补历史广告数据的美团成本
```

其中：

- `单次主任务成本`
  - 按上一节公式
- `单次日志 LLM 成本`
  - 只在 `SUCCESS` 记录生成 Markdown 时才可能产生
- `日志前补历史广告数据的美团成本`
  - 当前调用的是广告历史/广告明细/解密，按索引是免费
  - 所以当前人民币成本一般仍记 `0`
  - 但它会增加接口调用负载

## 4.3 日志 LLM 成本怎么估

当前仓库里，日志 LLM 服务会从返回值里读取 `totalTokens`，并写入记录明细。

估算公式分两种：

1. 如果模型服务商“输入/输出单价不同”

```text
LLM 成本
= prompt_tokens / 1_000_000 x 输入单价
+ completion_tokens / 1_000_000 x 输出单价
```

2. 如果你内部只按“总 token 单价”粗估

```text
LLM 成本
= total_tokens / 1_000 x 每千 token 单价
```

但要注意：

- 当前代码只稳定落了 `totalTokens`
- 如果模型服务商是“输入、输出分开计价”，那仅靠 `totalTokens` 只能做粗估，不能做精确核算
- 如果后面要做财务级核算，建议额外落库：
  - `promptTokens`
  - `completionTokens`
  - `model`
  - `provider`
  - `unitPriceSnapshot`

## 5. 按执行场景看成本

## 5.1 常规成功槽位

特征：

- 门店营业时间已存在
- 当前槽位可执行
- 已有窗口成功历史
- 不需要实时查询附近商家均价

美团调用：

- 计划状态查询 `1`
- 广告余额查询 `1`
- 解密若干次
- 实时广告明细 `1`

人民币成本：

- 美团付费接口成本：`0`
- 定价 LLM 成本：`0`
- 如果同步生成成功日志：再加一笔日志 LLM 成本

## 5.2 首次调价槽位 / 低峰基准价重算

在常规成功槽位基础上，额外可能发生：

- 查询附近商家平均出价 `1`
- 解密附近商家平均出价 `1`

人民币成本：

- 仍然通常是 `0`
- 因为附近商家平均出价接口和解密接口在索引里都是免费

## 5.3 营业时间缺失的槽位

在进入时段判断前，可能先发生：

- 查询门店详情 `/wmoper/ng/poi/detail` `1`

人民币成本：

```text
0.003 元 / 次
```

这是当前定价主链路里最明确、最容易被记入外部人民币成本的收费项。

## 5.4 成功日志首次补历史数据

成功记录生成 Markdown 前，系统可能补：

- 最近 7 天天级广告历史
- 昨天小时级广告明细
- 对应解密调用

人民币成本：

- 当前按索引仍为 `0`

但需要注意：

- 这是“首次成功日志”或“补偿重试”场景的额外负载
- 虽然不计费，但会显著增加这一次任务的外部调用次数和时延

## 6. 建议采用的两套报表口径

为了避免后面汇报时把“免费接口调用量”和“真实人民币成本”混在一起，建议同时保留两套口径。

### 6.1 财务成本口径

只看会产生人民币支出的部分：

```text
财务成本
= 美团收费接口成本
+ LLM token 成本
```

当前可直接落地为：

```text
财务成本
= 0.003 x N_门店详情补齐
+ 日志 LLM 成本
```

### 6.2 技术负载口径

看这次任务到底打了多少外部调用：

- 收费美团接口次数
- 免费美团接口次数
- 解密接口次数
- LLM 调用次数
- LLM 总 token 数
- 总耗时

这个口径不直接算钱，但对容量规划更有价值。

## 7. 建议的月度估算公式

如果你要先做月度预算，可以用这个简化版：

```text
月总成本
= 0.003 x 月度门店详情补齐次数
+ Σ(月度成功日志 totalTokens) 对应的 LLM 成本
```

如果只做粗估，也可以写成：

```text
月总成本
= 0.003 x 月度门店详情补齐次数
+ 月度成功日志次数 x 单次日志平均 LLM 成本
```

其中“单次日志平均 LLM 成本”可以先通过抽样 100 条成功记录估平均值。

## 8. 当前文档最重要的落地判断

- 当前“定价决策”本身，不要误算 LLM 成本。
- 当前“更新出价”接口虽然在链路里，但默认 `dry run`，不要误算成真实美团外呼成本。
- 当前“每次定价任务”的美团人民币成本，通常不是来自广告接口，而是来自少量收费管理 API 的偶发调用。
- 当前如果要做最接近真实花费的估算，优先盯这两个量：
  - `/wmoper/ng/poi/detail` 的实际调用次数
  - 成功日志 Markdown 的实际 `totalTokens`

## 9. 后续如果你要继续做精算

下一步最值得补的不是文档，而是埋点字段。建议把下面这些字段直接沉淀到记录表或统计表：

- `meituanPaidApiCostYuan`
- `mtPoiDetailCallCount`
- `mtFreeApiCallCount`
- `mtDecryptCallCount`
- `llmProvider`
- `llmModel`
- `promptTokens`
- `completionTokens`
- `totalTokens`
- `llmCostYuan`

这样后面就能从“估算”升级成“按记录汇总的实际成本报表”。
