## Context

当前 `user_behavior_event` 以门店为主体保存 H5 和管理后台事件，后端通过枚举限制事件类型，管理后台按门店聚合今日、近 7 天和近 30 天数据。业务从推广出价切换到评价自动回复后，旧事件调用方被删除但事件枚举和统计列仍有残留；当前客户端也没有会话标识、事件去重和结构化上下文约束。

自动回复与差评处理开关的每次成功保存已经由 `mt_comment_reply_setting_history` 在业务事务内记录来源、前后快照和时间。充值、知识库和评价处理结果也各有业务事实表，因此行为统计不应通过前端重复上报这些成功结果。

## Goals / Non-Goals

**Goals:**

- 建立与评价自动回复现行业务一致、语义稳定的 H5 和 PC 行为事件目录。
- 支持应用会话识别、事件去重、页面访问和关键行为路径分析。
- 修复支付、兑换码和 Tab 事件的失真问题。
- 将开关成功变更历史按来源和具体字段汇总到行为统计。
- 让当前可见但没有行为的门店也出现在统计结果中。
- 保持埋点失败不影响 H5 和管理后台主流程。

**Non-Goals:**

- 不采集设备指纹、商户个人身份或评价正文。
- 不建设通用数据仓库、实时流处理或第三方埋点平台。
- 不通过客户端埋点重复记录充值支付成功、知识库落库成功和评价处理成功。
- 不恢复任何旧推广策略、手动出价或 AI 高峰期功能。

## Decisions

### 1. 使用小规模稳定事件目录和结构化上下文

H5 事件统一为 `H5_APP_OPEN`、`H5_PAGE_VIEW`、`H5_SUPPORT_ENTRY_CLICK`、`H5_EXTERNAL_LINK_CLICK`、`H5_RECHARGE_SUBMIT_CLICK`、`H5_REDEMPTION_APPLY_RESULT`、`H5_LOG_DETAIL_EXPAND`、`H5_KNOWLEDGE_ACTION`；PC 事件为 `PC_COMMENT_LOG_VIEW`、`PC_KNOWLEDGE_VIEW`。

页面、入口、目标和结果通过受控的 `contextJson` 字段表达，避免继续为每个页面或按钮扩张事件枚举。旧推广事件不再接受，新客户端也不再产生旧 Tab、支付和兑换码事件。

备选方案是为每个页面和按钮建立独立事件。该方案 SQL 简单，但会重现当前事件目录膨胀、改版后大量遗留的问题，因此不采用。

### 2. 客户端生成会话和事件唯一标识

H5 和管理后台分别在当前页面应用生命周期内生成 `sessionId`，每次上报生成 `clientEventId`。数据库对非空 `client_event_id` 建立唯一索引，服务端遇到重复事件时按幂等成功处理。

应用打开事件由 H5 上报工具保证每个会话最多发送一次；所有页面访问通过 `H5_PAGE_VIEW` 携带 `pageCode` 和 `entrySource`。

### 3. 成功业务结果直接汇总事实表

行为统计从可见门店集合出发，左连接行为事件聚合和 `mt_comment_reply_setting_history` 聚合。开关历史通过前后快照判断具体字段是否真正发生变化，并按 `H5`、`ADMIN`、`SYSTEM` 来源分别计数。

备选方案是在设置保存成功后再写一条行为事件。该方案需要跨表双写并可能产生重复或不一致，因此不采用。

### 4. 仅记录可解释的有效行为

- 充值提交仅在前端校验通过后记录，携带算力数量、是否套餐和是否使用兑换码。
- 兑换码只记录应用成功或失败，不记录兑换码原文，也不再把面板展开和收起视为兑换码使用。
- 页面访问在页面真正展示时记录；Tab 点击本身不再作为访问量。
- 日志详情只在展开时记录，收起不计数。
- 知识库记录文档选择、预览结果、上传提交和 QA 表单等关键路径，具体动作用 `actionCode` 区分。

### 5. PC 上报权限与统计读取权限分离

PC 事件写入接口继续要求登录，并由服务校验当前用户对目标门店可见，但不再要求用户拥有行为统计页面的读取权限。行为统计查询仍要求 `analytics:user-behavior:list`。

### 6. 上下文校验和隐私边界

`contextJson` 必须为空或有效 JSON 对象，并限制长度。客户端不得上报 token、完整兑换码、手机号、评价正文、文件正文等敏感信息；允许的上下文只包含枚举编码、布尔值、数量和非敏感状态。

## Risks / Trade-offs

- [Risk] 新旧事件切换后近 30 天数据口径存在断点 → 旧明细保留，不复用旧事件名称；统计页明确展示新口径，最长 30 天后自然完成切换。
- [Risk] H5 页面销毁或外链跳转可能导致少量异步事件丢失 → 关键成功结果使用业务事实表，行为事件保持非阻塞且不影响主流程。
- [Risk] 通过 JSON 快照判断开关字段变化会增加 SQL 复杂度 → 只在最多 30 天的历史子查询中执行，并使用 `shop_id/create_time` 索引；未来数据量增长后可补充显式变更字段。
- [Risk] 可见门店作为统计基表会增加返回行数 → 延续分页和数据权限约束，并在聚合子查询中先按时间范围过滤。
- [Risk] 唯一事件重复插入可能触发数据库异常 → Mapper 使用幂等插入语义，重复事件返回成功且不影响业务页面。

## Migration Plan

1. 先增加可空的 `client_event_id`、`session_id` 字段和索引，旧数据无需回填。
2. 部署兼容新请求字段和新统计口径的后端。
3. 部署 H5 与管理后台新事件调用方，停止产生旧事件。
4. 更新行为统计页字段和展示。
5. 回滚时旧后端可忽略新增数据库字段；旧事件明细始终保留，不执行数据删除。
