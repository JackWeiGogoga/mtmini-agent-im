## Context

当前评价自动回复主链路由 `MtCommentReplyContentServiceImpl` 生成回复内容，再由 `MtCommentAutoReplyService` 调用美团添加商家回复接口。大模型回复已经成为主路径，商户知识库片段会作为高匹配 RAG 上下文补充。

美团 IM、评价和商家回复存在较严格的敏感词风控。风险来源包括模型自行生成、复述顾客评价、复述商户知识库内容，以及商户上传或手工维护了带有站外导流、极限宣传、医疗承诺、辱骂低俗等内容的知识。仅靠 prompt 约束不足以保证最终发送内容安全，因此需要本地词库检测、一次改写和兜底回复。

## Goals / Non-Goals

**Goals:**

- 使用配置文件维护首期敏感词词库，不依赖数据库后台管理。
- 对大模型生成回复进行本地敏感词检测，命中后最多重写一次。
- 重写后仍不合规时按评论类型从官方回复知识库随机选择兜底回复，官方无可用文案时再使用 `mt.comment.default-reply`。
- 对商户手工知识新增/编辑、文档上传解析生成的知识片段做敏感词拦截，命中时拒绝入库或标记解析失败。
- RAG prompt 上下文只允许使用高匹配且未命中敏感词的商户知识片段。
- 记录敏感词命中类别、处理动作、重写次数和兜底状态，便于排查自动回复质量。

**Non-Goals:**

- 首期不做敏感词后台管理、商户自定义词库或在线热更新。
- 首期不引入第三方内容安全审核 API。
- 首期不做复杂语义审核、模型分类器或机器学习判定。
- 首期不允许敏感商户知识以脱敏后形式入库；命中即拒绝。

## Decisions

### Decision: 敏感词使用配置文件管理

新增 `backend/src/main/resources/comment-reply-sensitive-words.yml` 或等价配置文件，按类别维护词条。每条词至少包含 `category`、`word`、`severity` 和 `enabled`。Spring 启动时加载为内存结构，检测服务只依赖本地内存，不增加运行时外部依赖。

替代方案是建表并提供后台管理。考虑首期需要快速落地且词库由平台统一维护，配置文件更简单；后续如果运营需要动态调整，再迁移到数据库。

### Decision: 检测前做文本归一化

新增 `CommentReplySensitiveWordService` 或等价服务。检测流程先归一化文本：小写、全角转半角、移除空白和常见标点、合并拆字变体，再做词库 `contains` 匹配。检测结果返回命中类别、命中词数量和最高风险等级。

归一化后的匹配会牺牲部分精确性，但首期目标是拦截明显风险词，优先降低违规发送概率。错误提示给用户展示命中类别，不直接展示完整敏感词列表，避免输出二次污染。

### Decision: 回复生成后检测，命中后只重写一次

大模型首次回复生成后执行敏感词检测。未命中则正常返回。命中时调用同一个 OpenAI-compatible chat 服务执行一次“合规改写”，输入原回复、评价摘要、命中类别和改写要求，要求模型保留服务态度但移除敏感表达。改写结果再次检测。

如果改写调用失败、改写为空或仍命中敏感词，则按当前评论类型从官方回复知识库随机选择兜底回复；官方无可用文案时再使用 `mt.comment.default-reply`。兜底回复也必须经过敏感词检测，命中时继续尝试下一条官方文案；若最终只能使用默认回复，默认回复也必须不命中词库。

替代方案是循环多次改写。考虑异步任务吞吐和大模型不确定性，首期只重试一次，避免单条评价长时间占用 worker。

### Decision: 商户知识入口前置拦截

手工 QA 新增和编辑时，对标题、问题、回答合并文本进行检测；命中则抛 `BusinessException`，新增/编辑失败。文档上传本身只做格式/大小/数量校验；异步解析出每个 chunk 后检测，任何待入库 chunk 命中敏感词时，本次文档解析标记 `FAILED`，不保存可用 chunk，并记录失败原因供 H5 展示。

替代方案是只过滤命中 chunk 并保留其他片段。考虑商户上传文档可能含系统性违规内容，首期采用整文档失败更容易让商户修正源文件，也避免部分违规知识漏入后续 RAG。

### Decision: RAG 上下文再做一次过滤

即使知识入库时已经检测，回复生成前将知识片段放入 prompt 时仍再做一次检测。命中敏感词的片段从本次上下文中剔除，并记录过滤数量。这样可以覆盖历史数据、词库更新后旧数据未重算等情况。

### Decision: 可观测性复用生成记录，必要时扩展字段

回复生成记录需要能看出敏感词处理结果。优先复用 `fallback_reason`、`error_stage`、`error_message` 和 `knowledge_hit_json` 等字段；如果字段表达不清，则新增 `sensitive_hit_json`、`rewrite_count`、`safe_fallback_used` 等字段。日志只记录类别、数量、阶段和 `shopId/commentId`，不记录完整违规内容。

## Risks / Trade-offs

- [Risk] 本地词库误杀正常表达 -> 错误提示展示类别，商户可修改知识；后续可加白名单或后台管理。
- [Risk] 词库无法覆盖全部变体 -> 通过归一化处理常见拆字、大小写和符号变体；后续根据线上命中与美团失败反馈迭代词库。
- [Risk] 改写再次生成敏感词 -> 只重写一次，失败立即走官方文案/默认回复兜底，保证最终回复可控。
- [Risk] 文档解析命中后整文档失败影响可用内容 -> 首期优先安全，H5 展示明确失败原因，商户修正文档后重新上传。
- [Risk] 历史已入库知识含敏感词 -> 回复生成前 RAG 上下文二次过滤，避免历史数据继续诱导模型。

## Migration Plan

1. 新增敏感词配置文件、配置绑定和检测服务，默认启用。
2. 接入回复生成后置检测、一次改写和官方文案/默认回复兜底。
3. 接入商户手工 QA 新增/编辑前置检测。
4. 接入文档解析 chunk 入库前检测，命中时标记文档解析失败。
5. 接入 RAG 上下文二次过滤和敏感词处理记录。
6. 补充单测后上线；如需回滚，可关闭敏感词配置或仅保留本地兜底，不影响美团接口调用。

## Open Questions

- 敏感词命中错误是否需要向商户展示具体词条。首期建议只展示类别，避免将违规词再次暴露在前端。
- 兜底回复来自官方回复知识库；是否需要对官方回复知识库也批量做历史敏感词治理，首期先通过回复兜底选择时检测规避。
